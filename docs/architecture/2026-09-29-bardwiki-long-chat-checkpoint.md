# 바드위키 체크포인트: 초장기 챗 기억과 자동 확장

- 작성일: 2026-09-29
- 상태: 사용자 논의에 따른 설계 체크포인트. 구현 완료 또는 성능 검증 보고서가 아니다.
- 범위: 공개판의 현재 체크아웃. 비공개판 동기화, 릴리스, 전체 위키 리부트는 포함하지 않는다.
- 실행 순서: 이 문서와 구현 계획을 먼저 커밋하고 push한 뒤 구현을 시작한다.
- 공식 계약: 작업공간 `project_wiki/`의 Markdown 정본, 고정 예산 컨텍스트, inquiry, 선택형 임베딩 계약을 기반으로 한다. 기존 공식 결정을 검토 없이 덮어쓰지 않는다. 동적 예산과 구간 편집 등 계약 확장이 필요한 내용은 이 문서에 제안과 합의로 명시한다.

## 1. 문제 제보와 확인 범위

0.9.48 무렵 작성한 위키를 0.9.51에서도 사용하는 장기 챗에서, 약 100턴 이후 캐릭터의 `지식과 비밀` 절이 매우 길어지고 바드챗 압축이 `직접 위키 갱신 1이 불완전합니다.`로 실패한다는 제보가 있었다.

처음의 '수동 수정'은 직접 편집인지 바드챗인지 불명확했으나 추가 제보에서 두 경로가 구분되었다. 문제 문서는 공백 포함 18,961자, 공백 제외 14,104자이며 자동 갱신으로는 계속 늘어나지만 직접 편집은 막힌다고 한다. 기본 간결화로 크게 줄이면 저장되지만, 원문과 `[[링크]]`를 유지하며 조금만 줄인 결과는 '직접 위키 갱신 1이 불완전합니다.'로 실패한다. 실제 문서와 실패 모델 응답은 아직 확보하지 않았지만 아래 경로별 제한 불일치는 코드에서 확인했다. 사용자는 문서 길이 제한을 다른 숫자로 높이지 말고 아예 제거하라고 명시했다.

현재 코드에서 확인한 별도 결함과 한계:

1. `src/ts/risubard/directWikiCommand.ts`의 응답 스키마와 parser에는 Markdown 12,000자 제한이 남아 있다. 제목, 유형, 본문 누락과 길이 초과가 같은 '불완전' 오류로 합쳐진다.
2. 바드챗은 입력 예산을 넘으면 기존 문서 본문을 앞부분만 남기도록 줄이면서, 모델에는 전체 문서 교체를 요구한다. 전달하지 않은 뒷부분이 사라질 위험이 있다.
3. `src/ts/risubard/wikiEmbeddingIndex.ts`는 문서별 최고 점수 구간 하나를 남기고 최대 12개 문서로 줄인다. 한 문서 안의 복수 근거와 후속 검토 기회가 제한된다.
4. 원문은 사건의 안정 메시지 ID 연결 또는 어휘 검색으로 회수한다. 사건 요약에서 생략된 상세 내용을 다른 표현으로 묻는 경우가 취약할 수 있다.
5. 인공 벡터를 사용하는 회귀 테스트는 검색 연결과 범위 보존을 확인하지만 실제 한국어 초장기 챗의 회수율을 입증하지 않는다.
6. 일반 tokenizer의 제한된 문자열 캐시는 있으나, 조사한 경로에서는 챗 전체 누적 토큰 집계를 유지하는 장치가 확인되지 않았다.
7. `src/lib/Others/RisuBardWikiEditor.svelte` 본문 textarea에는 `maxlength="12000"`이 남아 있다. 수동 저장 클라이언트와 서버의 Markdown 정규화에는 같은 글자 제한이 없다. 따라서 자동 생성 가능한 문서를 입력창에서 정상 수정할 수 없는 불일치가 있다.

결론: 즉시 고칠 문제는 자동 저장, 직접 편집, 바드챗 사이의 인위적인 본문 글자 제한 불일치다. 분할이나 강한 압축으로 이 결함을 우회하게 하지 않는다. 문서의 저장 및 편집 글자 제한은 없애되, 모델 요청 예산, 출력 잘림 검증, HTTP 전송 안전장치와 충돌 검증은 별개로 유지한다. 모델에 전문을 전달할 수 없는 경우 조용히 잘라 전체 교체하지 않는다.

## 2. 최종 목표

- 수백, 수천 턴 및 수백만 토큰 이상에서도 현재 인물 상태를 다루기 쉽게 유지한다.
- 과거를 요약에서 지웠다는 이유로 회수 불가능하게 만들지 않는다. 원본 대화와 사건 근거를 보존한다.
- 저장량과 모델에 전달하는 양을 분리한다. 문서가 길어도 필요한 구간만 읽고 수정한다.
- 사용자가 바드챗에서 주기적으로 수동 압축해야만 유지되는 구조를 피한다.
- 토큰은 채워야 하는 할당량이 아니라 상한이다. 관련 자료가 적으면 덜 사용한다.
- 초장기 챗에서는 사용자가 허용한 범위에서 예산을 자동 증가시킬 수 있다. 기본값은 자동 증가 없음이다.
- 완벽한 규모 추정보다 간단한 설정과 예측 가능한 처리 비용을 우선한다.

## 3. 저장 구조와 캐릭터 문서

Markdown 정본과 원본 채팅을 유지한다. 별도 graph를 새로운 지식 정본으로 도입하지 않는다.

| 자료 | 역할 | 모델에 전달하는 범위 |
| --- | --- | --- |
| 캐릭터 문서 | 정체성, 현재 상태, 관계, 현재 지식과 제약 | 핵심 상태와 해당 주제 구간 |
| 주제별 상세 문서 | 복잡한 관계, 비밀 공유 범위, 미해결 약속 등 | 필요한 주제 구간 |
| 캐릭터 연대기 | 해당 인물의 사건과 역사를 시간순으로 탐색 | 관련 사건 항목 |
| 사건 문서 | 누가 무엇을 했고 어떤 변화가 있었는지 | 관련 사건의 근거 구간 |
| 원본 대화 | 정확한 대사, 행동, 소품, 맥락 | 확인에 필요한 원문 구간 |
| 파생 검색 색인 | 어휘, 의미, 인물, 시간과 출처 연결 | 모델에 전체 직렬화하지 않음 |

캐릭터 문서의 고정 크기 강제보다 한 번에 모델이 읽고 수정하는 크기를 제한하는 것이 최종 방향이다. 직접 텍스트 편집에는 별도의 본문 글자 제한을 두지 않는다. 전체 정보는 늘어날 수 있다. 필요하면 주제를 분리하지만 자동 글자 수 절단이나 유효 사실 삭제로 크기를 맞추지 않는다. 분리 문서는 하나의 인물 ID에 연결하며 같은 인물을 별개의 인물로 중복 등록하지 않는다.

기존 H3 절 단위 갱신보다 작은 주제 구간을 식별할 수 있어야 한다. 긴 `지식과 비밀` 안에서도 왕위 계승, 특정 인물의 배신, 다른 인물의 정체, 탈출 계획을 각각 선택하고 갱신한다. 안정 식별자와 content hash로 변경 충돌을 검사하고 전달하지 않은 구간은 프로그램이 그대로 보존한다.

현재 상태를 갱신할 때는 과거 상태를 현재 상태와 나열해서 계속 쌓지 않는다. '배신을 의심했다'에서 '배신을 확인했다'로 바뀌면 현재 상태를 바꾸고 과거 과정은 사건에서 찾는다. 누가 언제 알았는지, 오해인지 사실인지, 공유한 비밀인지 구분한다. 부분 입력으로 문서 전체의 모든 모순을 검증했다고 주장하지 않는다.

## 4. 캐릭터 연대기

각 캐릭터의 전체 행적을 따로 탐색할 수 있게 한다. 기본 구현은 기존 사건과 원문 연결에서 생성하는 읽기 전용 파생 연대기다. 사건을 다시 요약하는 별도 모델 호출을 매 턴 추가하지 않는다.

- 사건 ID, 안정 메시지 ID, 인물의 참여나 지식 변화에 대한 근거, 기록 순서를 이용한다.
- 명시적 작중 시간이 있으면 표시하되, 불명확한 시간이나 회상 순서를 추측하지 않는다.
- 이름 언급만으로 직접 참여, 행동 또는 지식 취득을 단정하지 않는다.
- 사건 수정과 철회가 반영되어야 하며 별도 수동 작성 사본과 불일치하지 않아야 한다.
- 사용자에게 긴 연대기를 보여줄 수 있지만 모델은 필요한 부분만 읽는다. 큰 연대기는 페이지나 구간으로 읽는다.
- 원문에 있지만 사건 요약에 없는 상세 정보까지 찾을 수 있도록 관련 원문 경로를 보존한다.
- '모든 행적'은 원문의 모든 행동이 자동 추출됐다는 보증이 아니다. 출처 누락과 인물 연결이 불확실한 기록은 숨겨서 완전한 기록처럼 표시하지 않는다.
- 기본 인물 문서에 전체 연대기 링크를 끝없이 나열하지 않고 파생 색인에서 목록을 관리한다.

## 5. 검색 개선

흐름: 현재 입력과 최근 장면 해석 → 어휘 및 의미 검색 → 인물과 시간 단서로 후보 확장 → 근거 구간 선택과 재순위 → 원문 확인 → 실제 예산 안에서 전달.

1. 현재 문구와 최근 장면 문맥으로 검색한다. '그때 약속'처럼 표현이 모호해도 등장인물과 장소가 단서를 제공할 수 있다. 검색용 추측은 정본 사실로 저장하지 않는다.
2. 사건 요약 외에 원문 구간도 검색 대상으로 삼는다. 원문 구간 색인은 파생 자료이고 변경된 자료만 갱신한다.
3. 문서별 한 구간으로 일찍 축소하지 않고 필요한 복수 근거를 검토한다.
4. 로컬 검색 후보 수와 AI에 전달하는 최종 토큰을 분리한다. 후보 증가가 곧 모델 입력 증가를 뜻하지 않게 한다.
5. 근거가 부족할 때만 제한된 후속 탐색을 검토한다. 별도 AI 질의 생성과 재순위 호출도 비용에 포함한다. 정확도 명목으로 호출 수와 예산을 조용히 증가시키지 않는다.
6. 현재 상태와 과거 사건을 혼동하지 않고, 여러 사건을 비교해야 하는 질문에서는 필요한 근거 집합을 함께 제공한다.
7. 기존의 context 제외, 철회 사건 제외, OOC 정책, 안정 출처와 hash 검증을 유지한다.

임베딩 미사용, 준비 중, 실패 상태를 실제 의미 검색이 작동하는 상태와 구분해서 평가한다. 임베딩 사용을 몰래 활성화하거나 새 외부 제공자로 사용자 자료를 전송하지 않는다.

## 6. 동적 예산: 합의와 대체된 제안

처음에는 모든 토큰을 지금 수준으로 고정하는 방향을 논의했다. 이후 사용자가 초장기 챗의 성능을 위해 허용한 최대치까지 자동 증가하는 설정을 요청했다. 이것이 최신 요구다.

처음의 '토큰 동적 계산' 숫자 입력과 항목별 증가 계수는 최종 UI로 채택하지 않는다. 사용자는 드롭다운 하나로 일괄 제어하는 단순한 구성을 원한다.

누적 토큰 수를 매번 스캔하거나 토큰화하지 않는다. 최초 스캔 및 캐시 재구축 비용을 피하기 위해 활성 AI 응답 수를 턴 규모로 사용한다. 사용자 메시지를 포함한 단순 배열 인덱스와는 구분한다. 삭제, 비활성 기록과 분기를 현재 챗 기준으로 처리한다. 정확한 규모 추정이 필수는 아니다.

내부 계산은 기준 턴 이후 규모가 두 배가 될 때 일정량 증가하는 완만한 식을 우선 실험한다.

```text
성장량 = max(0, log2(max(1, 활성 AI 턴 수 / 기준 턴 수)))
실제 토큰 한도 = min(최대 허용 토큰, 기본 한도 + 모드별 증가량 × 성장량)
```

기준 턴 수, 모드별 계수, 반올림과 후보 수 안전 상한은 구현과 평가에서 결정할 값이다. 대화에서 나온 10만 토큰, 100턴, 1,000토큰 증가, 6,000/12,000토큰 등의 수치는 설명용 예시이며 확정 제품 기본값이 아니다. 숫자를 정할 때 문서와 툴팁도 함께 맞춘다.

자동 증가 대상으로 권장한 항목:

| 항목 | 정책 |
| --- | --- |
| 사건 검색 토큰 | 우선 적용 |
| 과거 원문 회수 개수 | 우선 적용. 0으로 끈 회수를 임의로 켜지 않음 |
| 로컬 검색 후보 수 | 우선 적용. AI 재순위 입력 한도와 분리 |
| 일반 기억 검색 토큰 | 우선 적용 |
| 분석 및 갱신 입력 예산 | 후속 검토. 현재 설정이 출력 한도와 결합된 경로는 먼저 분리 검토 |
| 자료별 토큰 상한 | 기본적으로 고정 |
| 최근 대화 턴 수, 답변 출력 토큰 | 자동 증가하지 않음 |
| 자동 정본 갱신 대상 수, 재시도 횟수, 검색 대기 시간 | 자동 증가하지 않음 |

모든 세부 예산은 전체 실제 검색 한도 안에서 경쟁한다. 모델의 실제 컨텍스트 용량에서 정적 프롬프트, 최근 대화, 출력 예약 등을 제외한 가용량도 넘을 수 없다. 설정 한도, 요청 시 실제 가용 한도, 실제 사용 토큰을 혼동하지 않는다. 자료가 적으면 여유를 비워 둔다.

## 7. 최종 UI

기존 설정 화면에 `장기 기억 자동 확장` 드롭다운 하나를 제공한다.

| 선택 | 의미 |
| --- | --- |
| 사용 안 함 | 기본값. 기존 사용자가 정한 한도 유지 |
| 절약형 | 로컬 검색 후보 중심으로 확장하고 토큰 증가는 작게 |
| 균형형 | 후보, 사건, 원문 회수 예산을 함께 확장 |
| 회수 우선형 | 과거 근거를 더 넓게 탐색하고 읽을 수 있게 확장 |

- 켰을 때만 `최대 허용 토큰` 입력과 현재 턴 기준 실제 한도를 표시한다.
- 기본 설정값을 덮어쓰지 않는다. 자동 확장을 끄면 기존 값으로 돌아간다.
- 기본 화면에 항목별 동적 계수, 수식, 후보 수 제어를 추가하지 않는다.
- 제목에 마우스를 올리거나 모바일에서 제목을 터치하면 설명을 연다. 키보드로도 열고 닫을 수 있어야 한다.
- 툴팁에 선택의 비용과 숫자의 의미, 상한이지 반드시 채우는 양이 아니라는 점을 설명한다.
- 계산 내역은 펼쳐 볼 수 있게 하되 기본 화면에서는 숨긴다.
- 예시 표시는 `실제 검색 한도 8,000토큰 = 기본 6,000 + 동적 증가 2,000`이다. 상한으로 제한되면 그 사실을 표시한다.
- 저장, 재열기, 챗별 설정, 전역 기본값과 봇 고정 설정의 기존 우선순위를 유지한다.
- 실제 데스크톱과 모바일 크기에서 화면과 클릭, 터치, 입력, 저장 유지 여부를 검증한다.

## 8. 회수 품질 목표와 검증

80%와 96%는 목표이며 현재 달성한 수치가 아니다.

- 정확한 키워드 없이 문맥과 바꿔 말한 표현만 제공: 최종 모델 입력에 답에 필요한 근거가 포함되는 비율 80% 이상 목표.
- 식별 가능한 이름, 장소, 물건이나 표현 제공: 같은 기준으로 96% 이상 목표.
- 문맥에도 단서가 없는 질문은 모호한 질문 집합으로 따로 평가한다. 불리한 실패를 임의로 제외하지 않는다.
- 복수 사건 질문은 필요한 근거 집합을 모두 회수해야 완전 성공이다.
- 검색 후보 적중, 최종 구간 적중, 답변 정확도를 구분한다. 주체, 시점, 인물별 지식 경계와 없는 사실을 만들어내지 않는 능력도 평가한다.
- 압축 및 구간 분리 전후 같은 질문의 회수율을 비교한다.
- 100/1,000/5,000/10,000턴과 긴 실제 본문 조건을 나누어 평가한다. 짧은 챗 점수로 긴 챗 실패를 가리지 않는다.
- 비슷한 사건, 반복 약속, 관계 변화, 오해 정정, 초반의 작은 행동을 포함한다. 무관한 문장 반복만으로 길이를 채우지 않는다.
- 개발용 이야기와 최종 평가 이야기를 분리한다. 실제 모델과 임베딩 구성, 표본 수, 실패 수와 불확실성을 보고한다.
- 모델 호출 총 입력/출력 토큰, 대기 시간, 로컬 검색 시간, 색인 크기와 문서 크기를 함께 측정한다.

외부 평가 참고: [LongMemEval 원 논문](https://arxiv.org/abs/2410.10813). 시간 추론, 지식 갱신, 여러 사건 결합, 답할 수 없는 질문의 구분을 참고하되 외부 점수를 제품 성능으로 전용하지 않는다.

## 9. 구현 순서와 완료 구분

1. 체크포인트 문서와 첫 실행 계획만 선택 커밋하고 `rpaddict`로 push한다. 작업공간의 다른 미커밋 변경을 섞지 않는다.
2. 첫 구현은 직접 편집기의 maxlength와 바드챗 스키마 및 parser에 남아 있는 본문 글자 제한을 모두 제거하고, 원문 절단 후 전체 교체 결함을 회귀 테스트로 재현하고 수정한다. 18,961자 이상 문서의 키보드 입력, 저장, 재열기와 바드챗의 완전한 본문 및 링크 전달을 확인한다. 전체 원문을 모델 예산에 넣을 수 없는 작업은 자료를 임의로 자르지 않고 명확히 중단한다. 이것만으로 대형 문서의 부분 편집이 구현되는 것은 아니다.
3. 동적 예산 계산과 드롭다운을 실제 조회 경로에 연결한다. 정책 선택만 저장하고 효과가 없는 UI는 만들지 않는다. 입력 예산과 출력 한도를 혼동하지 않는다.
4. 부분 구간 읽기와 충돌 안전 편집, 캐릭터 연대기와 원문 구간 검색을 연결한다. 각 단계의 기존 파일 정본 호환성을 확인한다.
5. 실제 장기 챗 평가로 후보 수와 모드별 계수를 조정하고, 기존 문서는 백업과 재개 가능한 이관 절차를 제공한다. 전체 리부트를 필수로 강요하지 않는다.

체크포인트, 최초 안전 수정, 자동 확장 UI, 연대기, 부분 편집, 회수율 목표 달성은 서로 다른 완료 상태다. 일부 구현을 전체 초장기 기억 개선 완료로 보고하지 않는다.

## 10. 아직 확정하지 않은 구현 세부

- 부분 구간 ID의 Markdown 표현과 수동 편집 시 재결합 규칙.
- 연대기 인물 연결의 구체적인 메타데이터 형식과 기존 자료의 누락 표시.
- 원문 의미 색인과 로컬 어휘 색인의 세부 저장 형식 및 증분 갱신 경로.
- 모드별 숫자 계수와 안전 상한. 프로파일링과 회수 평가로 결정한다.
- 검색 및 분석 예산의 실제 모델 가용 컨텍스트 연결 방식.

이 항목들은 개발자가 합의된 구조와 기존 코드에 맞게 결정하고 근거를 기록할 구현 선택이다. 미확정 숫자를 사용자 합의 또는 성능 보증으로 표시하지 않는다.

## 11. 2026-09-29 구현 결과

체크포인트 `c286fe6`을 먼저 공개판 main에 push한 뒤 아래 기능을 구현했다. 첫 제한 제거에서 멈춘 범위는 사용자의 후속 지시에 따라 전체 실행 계획으로 대체했다. 구현 코드는 현재 작업 공간의 변경이며 체크포인트 커밋 자체에 들어 있지 않다.

- 직접 편집과 바드챗 본문의 12,000자 상한을 제거했다. 실제 모델 토큰 상한, 저장 구조와 충돌 검증은 유지한다.
- 긴 단일 문서의 바드챗 수정은 전문을 작은 구간으로 나누고 모든 구간의 응답을 검증한 뒤 한 번 저장한다. 구간 ID는 원문 위치와 SHA-256에서 만들며 정본에 별도 표식을 삽입하지 않는다. 유지 응답은 원문 바이트를 그대로 사용한다. 여러 문서 결합과 메타데이터 변경은 이 부분 편집 경로에서 지원하지 않으며 불완전한 처리 대신 중단한다. 각 호출은 예산 안에 있지만 큰 문서 전체를 처리하는 총 호출 수와 총 토큰은 증가할 수 있다.
- 전역 및 현재 챗 설정에 자동 확장 드롭다운을 연결했다. 기본 off, 기준 100 AI 응답, 두 배 성장마다 절약형 500 / 균형형 1,500 / 회수 우선형 3,000토큰 증가, 초기 최대 허용 기본값 12,000토큰이다. 이 숫자는 초기 조정값이며 정확도 보증이 아니다. 실제 요청과 표시가 같은 계산기를 사용한다.
- 사건의 정확한 인물 링크와 역링크로 읽기 전용 연대기를 생성한다. 20개씩 표시하고 모호한 연결과 누락 출처를 알린다. 기존 문서와 원문을 복제하거나 기존 자료를 자동 분할하지 않는다. 별도 이관이나 전체 리부트가 필요하지 않다.
- 로컬 후보와 최종 입력량을 분리하고 같은 문서의 독립적인 근거 구간을 최대 3개 보존한다. 재순위화 후에도 원문 위치와 hash를 검증한다.
- 선택형 임베딩이 켜져 있으면 활성 과거 원문도 검색한다. 변경되지 않은 원문은 청크와 벡터를 재사용하고, 질의 벡터는 위키 검색과 짧은 메모리 캐시를 공유한다. 최근 원문, OOC, 비활성 기록은 후보 정렬 전에 제외하고 현재 본문 및 역할을 다시 검사한다. 챗 전환과 설정 변경은 이전 작업과 결과를 무효화한다. 초기 색인이 준비되지 않거나 실패하면 기존 검색으로 진행한다.
- 원격 임베딩 사용 시 새 원문 구간도 이미 선택한 제공자에 전송된다. 자동 확장 선택만으로 임베딩을 켜지 않는다. 최초 과거 원문 색인 비용과 저장 공간은 대화량에 비례한다. 매 턴 대화 전체를 다시 토큰화하지는 않지만 현재 로컬 후보 검사 자체는 선형 순회를 포함한다.

일반 자동 정본 작성의 기존 H3 패치 규칙과 개인 프리셋은 유지한다. 문서 크기를 강제로 줄이거나 인물별 모든 행동이 추출되었다고 보증하는 기능은 아니다. 큰 저장 문서를 부분적으로 읽고 회수하는 기반과 관리자 구간 수정, 파생 연대기를 제공한다.
