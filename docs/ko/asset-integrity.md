# 에셋 무결성 검사와 저장 성능

일반 채팅 저장은 에셋 전체 검사가 아니다. V3의 에셋 동기화는 앱에서 추가하거나 교체하고 제거한 참조를 폴더에 반영한다. 변경하지 않은 에셋을 서버 재시작이나 캐시 재로딩만으로 전부 다시 읽지 않는다.

## 검증 경계

- **KV 원본:** 내용의 SHA-256을 객체 ID로 사용한다. 원본을 실제로 읽을 때 내용 해시를 검증한다. 같은 키의 객체 ID가 달라지면 변경으로 처리한다.
- **폴더 동기화:** 체크섬 검증을 거쳐 읽은 기존 소유권 인덱스의 키, 내용 해시와 크기를 비교한다. 그대로인 참조는 재사용한다. 새 파일은 원본을 검증한 뒤 기존 journal로 게시한다. 삭제와 교체로 퇴역시킬 복사본은 내용 검증 및 transaction 선행조건을 유지해 미반영 외부 편집을 덮어쓰지 않는다.
- **외부 편집 감지:** 실제 SHA-256을 검사한 파일의 크기, 나노초 수정 시각과 변경 시각, 파일 및 장치 식별자, 생성 시각을 함께 기록한다. 재시작 뒤에도 이 값이 같으면 이전 해시를 재사용한다. 달라진 파일은 다시 읽고, 읽기 전후 식별 정보를 비교한다. 파일 감시 이벤트가 없는 경우에도 기존 stat 탐색을 유지한다.
- **명시적 재검증:** 캐릭터 전환 및 재검증 기능의 원본과 복사본 SHA-256 검사는 유지한다. 큰 자료의 최초 복사와 명시적 전체 검증은 일반 채팅 저장과 비용이 다르다.

파일 식별 정보는 변경 탐지 수단이며 암호학적 무결성 증명은 아니다. 악의적으로 식별 정보를 위조하거나 파일 정보가 바뀌지 않는 저장장치 손상까지 증명하지 않는다. 이런 검증에는 실제 내용 해시 검사가 필요하다. 기존 검사 기록이 없는 복사본은 최초 한 번 내용을 확인한 뒤 재사용 정보를 기록한다. 백업 복원이나 다른 파일시스템으로 복사해 파일 식별자가 바뀌면 다시 검사한다.

## 회귀 방지 기준

실행 시간만으로 합격시키지 않는다. 빠른 개발 PC에서도 불필요한 읽기가 들어오면 다음 테스트가 실패해야 한다.

1. 기존 V3 자료를 다시 열거나 인덱스를 reload한 뒤 변경 없는 `sync()`는 에셋 본문 읽기와 인덱스 쓰기 0건이다.
2. 캐릭터 에셋 하나를 바꿔도 관계없는 에셋 본문을 읽지 않는다.
3. 검증 기록이 있는 외부 파일은 재시작 후 본문을 재독해하지 않는다.
4. 같은 크기의 편집, mtime 복원, 파일 교체 및 삭제는 계속 감지한다.
5. 검사 중 파일 변경, 손상된 인덱스, 외부 편집 직후 앱 삭제 경합과 journal 게시 중단은 안전하게 거절하거나 복구한다.
6. KV 원본 내용이 손상되면 실제 읽기에서 여전히 SHA-256 오류를 낸다.

관련 테스트는 `server/node/character-assets.test.ts`, `live-character-files.test.ts`, `live-files-stability.test.ts`에 있다. 저장 로그의 `assetSyncMs`는 에셋 동기화 비용을 별도로 기록한다. 이전 로그의 `revisionAcceptMs`에는 이 비용도 포함돼 있으므로 변경 전후 값을 그대로 비교하지 않는다.

## 검토한 기술

2026-09-24 기준 공식 문서를 검토했다.

- [Git index와 파일 감시](https://git-scm.com/docs/git-update-index): 변경 정보로 불필요한 본문 검사를 줄이는 접근을 참고했다. 파일이 바뀌지 않았다고 무조건 가정하는 옵션을 도입한 것은 아니다.
- [Node.js 파일 감시 제약](https://nodejs.org/api/fs.html#caveats): 운영체제별 차이와 이벤트 누락 가능성이 있어 감시 이벤트만으로 무결성을 판정하지 않는다.
- [Linux fs-verity](https://docs.kernel.org/filesystems/fsverity.html): Merkle tree를 이용해 읽는 데이터 블록을 검증할 수 있지만, 지원 파일시스템의 읽기 전용 파일을 대상으로 한다. Windows와 사용자가 수정하는 에셋 폴더에 공통 적용할 수 없어 이번 수정에서는 도입하지 않았다.

SHA-256을 다른 해시 함수로 교체하는 것보다 불필요한 전체 읽기와 중복 탐색을 제거하는 것이 이번 문제에 직접적인 해결이다. 새 라이브러리나 플랫폼 전용 의존성은 추가하지 않는다.
