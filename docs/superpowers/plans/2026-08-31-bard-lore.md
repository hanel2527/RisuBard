# Bard Lore Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use executing-plans to implement this plan task-by-task.

**Goal:** Preserve imported legacy lorebooks while adding a RisuBard Bard Lore mode that selects only scene-relevant entries under user-editable, persisted entry and token budgets without an LLM at generation time.

**Architecture:** Store an independent Bard Lore state on each character, derived from but not mutating legacy lore content. A pure deterministic retriever selects `required`, direct-key, sparse-ranked, and explicitly linked entries. The existing prompt pipeline receives only the selected character entries while legacy mode remains byte-for-byte compatible.

**Tech Stack:** TypeScript, Svelte 5, Vitest, existing RisuAI tokenizer and lorebook pipeline.

---

## Scope and invariants

- Legacy `globalLore` remains available and export-compatible.
- Upgrade copies full entries; it never promotes every `alwaysActive` entry to `required`.
- Retrieval never expands merely because two entries share a type or tag.
- Runtime retrieval performs no model call and never feeds selected lore text back into its own query.
- `targetTokens`, `maximumTokens`, and `maxEntries` are enforced before prompt assembly.
- Required entries fail visibly when they alone exceed the maximum instead of being silently truncated.
