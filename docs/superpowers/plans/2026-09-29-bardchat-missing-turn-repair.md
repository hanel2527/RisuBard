# 바드챗 누락 턴 복구와 작중 행적 보완 계획

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**상태:** 계획 재확인만 완료. 아래 기능은 아직 구현하지 않았다. 인물 연대기 롤백과 별도 작업이다.

**2026-09-30 후속 범위:** 사용자가 별도로 요청한 개별 재분석의 사건 순서 수정은 아래 범위 복구 기능과 분리한다. `eventOrder.ts`에서 사건의 `sourceMessageIds`를 현재 챗 메시지 배열 위치로 해석하며, 표시 턴 번호나 분석 완료 시각을 정렬 키로 저장하지 않는다. 이야기 목록, 사건 폴더, 직전 사건 선택 및 새 아크플롯 묶음에 적용한다. 기존 사건을 덮어쓰는 개별 재분석은 생성 시각도 보존한다. 원본 위치가 불명확한 사건은 화면 뒤쪽에 표시하고 새 분석의 직전 사건이나 아크 묶음에는 넣지 않는다. 계승 체크포인트만 현재 챗 이전 경계로 인정한다. 이미 작성된 아크플롯 본문의 소급 재작성은 하지 않는다.

**Goal:** 바드챗에서 지정한 과거 턴의 누락 사건을 원문으로 복구하고, 요청한 경우 관련 인물의 작중 행적만 보완한다.

**Architecture:** 자연어 요청을 검증된 턴 범위와 작업 종류로 변환하고, 프로그램이 현재 채팅의 실제 메시지 ID와 원문을 확정한다. 기존 분석과 사건 저장의 구성요소는 재사용하되, 기존 재분석 전체를 그대로 반복 호출하지 않는다. 누락 사건 생성과 행적 보완에만 쓰기 권한을 주고 기존 세이브를 복구 경계로 사용한다.

**Tech Stack:** Svelte 5, TypeScript, 기존 Node Markdown 위키 서비스, Vitest, 브라우저 실행 검증. 새 의존성 없음.

**Spec:** 이 문서의 사용자 요구와 범위가 이번 기능의 제안 명세다. 사용자 요청은 `140~144턴의 누락 사건 복구`와 `관련 캐릭터의 작중 행적 보완`이다. 저장 권위와 원문 연결은 공개판 저장소 루트 기준 `../project_wiki/markdown_narrative_wiki.md` 등 프로젝트 상위 공식 위키를 따른다. 공식 위키 계약 변경이 필요하면 별도 검토하고 자동으로 덮어쓰지 않는다.

## Global Constraints

- 이번 승인 범위는 인물 연대기 롤백과 이 계획 재확인까지다. 복구 기능 구현과 릴리스는 이번 작업에 포함하지 않는다.
- 자동 문서 분할, 별도 인물 상세 문서, 인물 연대기 재도입, 전체 리부트는 포함하지 않는다.
- 일반 바드챗 편집 및 기존 수동 재분석의 동작을 암묵적으로 변경하지 않는다.
- 원본 메시지, swipe, 메시지 순서, 기존 사건 본문과 메타데이터를 수정하지 않는다.
- 기존 인물의 행적 절만 보완한다. 현재 상태, 관계, 지식, 다른 문서 유형은 바이트 단위로 보존한다.
- 인물이 없거나 제목과 별칭이 충돌하면 새 인물 문서를 추측 생성하지 않는다. 미적용 이유를 표시한다.
- 모델이 프로그램 관리 ID, 파일 경로, 원문 출처를 만들 수 없다. 사용자가 문서 ID를 찾을 필요가 없다.
- 검사 결과만으로 사건 누락과 분석 실패를 혼동하지 않는다. 철회, OOC 제외, 원문 변경, 출처 모호함은 자동 재생성 대상에서 제외한다.
- 기존 분석 토큰 상한을 지키고 턴별로 처리한다. 긴 턴을 조용히 자르거나 여러 턴 전체를 한 요청에 넣지 않는다.
- 실행 시작의 characterId/chatId/메시지 ID를 고정한다. 화면 전환은 작업의 쓰기 대상을 바꾸지 않는다.
- 사용자 데이터에서 시험하지 않는다. 짧은 합성 대화와 임시 저장 폴더에서 검증한다.

## Review Focus

1. 표시된 턴 번호와 실제 원문의 일치: user/assistant 교대, OOC, 비활성, 삭제, 첫 메시지, swipe를 포함한다.
2. 중복 및 덮어쓰기 방지: 기존 사건, 묶음 사건, 재시도, sourceMessageIds 구성 차이를 포함한다.
3. 행적 외 정보 보존: AI가 현재 상태나 관계 변경을 제안해도 프로그램이 거부한다.
4. 중단 및 동시 변경: 두 번째 턴 저장 실패, 취소, A/B 전환, 원문 및 위키 외부 편집을 포함한다.
5. 복원: 프로그램 재시작 뒤에도 작업 전 채팅, 분석 영수증과 위키로 돌아갈 수 있어야 한다. 복원 후 새로 쓴 대화가 사라질 수 있는 전체 세이브 복원이라는 범위를 명확히 표시한다.

## Task 1: 요청 해석과 읽기 전용 대상 확인

**Files:** 새 `src/ts/risubard/bardChatTurnRepair.ts` 및 `.test.ts`; `src/ts/process/index.svelte.ts`; 기존 `chatTurnNavigation.ts`, `memoryAnalysisClient.ts`의 투영 함수 재사용.

**Interfaces:** `TurnRepairRequest = { fromTurn: number; toTurn: number; repairMissingEvents: boolean; supplementHistory: boolean }`. 해석 결과는 생성 ID가 아니라 이 요청만 반환한다. `prepareTurnRepair`는 고정된 chat ID, 메시지 ID, 원문 hash, 연결 사건 ID, `missing | existing | excluded | ambiguous | unavailable` 상태를 턴마다 반환한다.

- [ ] 짧은 대화로 범위 파싱, 표시 번호 일치, 잘못된/역순/범위 밖 번호, 다른 챗 참조 거부 테스트를 먼저 작성하고 실패를 확인한다.
- [ ] `140~144턴`처럼 명확한 숫자 범위는 로컬에서 해석한다. 자연어 판별이 필요하면 엄격한 구조화 결과를 검증한다. 복구 의도를 판별할 수 없으면 일반 편집기로 조용히 넘겨 신규 사건 생성을 시도하지 않고 구체적인 형식을 안내한다.
- [ ] 현재 UI의 턴 번호를 사용해 ID를 고정한 다음 OOC 등 분석 제외 조건을 적용한다. 제외 턴을 빼고 번호를 다시 매기지 않는다.
- [ ] 날짜, 볼륨, 챕터가 함께 주어지면 대상 원문과 대조한다. 불일치하거나 날짜만으로 여러 후보가 나오면 쓰기 없이 대상을 다시 지정하게 한다.
- [ ] 화면에 로드되지 않은 메시지를 확인할 수 없으면 정상 hydration 경로로 읽거나 준비 실패를 알린다. 없는 원문을 추측하지 않는다.
- [ ] 기존 사건의 sourceMessageIds와 실제 대상 assistant ID를 대조한다. 단순 제목 비교나 문서 개수 비교로 누락을 판정하지 않는다.
- [ ] 대상 턴, 제외 사유, 예정 작업을 먼저 표시한다. 명시적으로 지목한 턴은 이번 복구의 필수 원문 자료임을 표시하고, 일반 바드챗의 최근 챗 참고 자료 선택과 구분한다.
- [ ] 대상 확인은 모델 분석 및 위키 저장을 시작하지 않는다. 관련 테스트 통과 후 검토 가능한 단위로 커밋한다.

- [ ] 세이브 복원 테스트를 통과하기 전에는 다음 저장 기능을 활성화하지 않는다.

## Task 3: 누락 사건만 생성

**Files:** `src/ts/process/index.svelte.ts`; `src/ts/risubard/memoryAnalysisClient.ts`; `server/node/risubard-memory-analysis.ts`; `server/node/risubard-markdown-wiki.ts` 및 각각의 테스트.

**Interfaces:** 복구 분석에는 검증된 대상 원문과 앞선 제한 문맥을 전달한다. 서버의 복구 전용 사건 저장은 대상 assistant ID와 기대 source hash를 받아 `created | already-exists | conflict`로 응답한다. 기존 `saveConfirmedTurn` 전체 동작은 바꾸지 않는다.

- [ ] 중간 두 턴만 사건이 없는 짧은 대화 테스트를 먼저 만든다. 이미 있는 사건은 본문, created 시각, storyTime과 ID가 동일하게 유지되어야 한다.
- [ ] 일반 재분석 함수 전체 호출 대신 기존 분석, 검증과 ID 생성 구성요소를 재사용하는 사건 전용 경로를 만든다. 자동 정본 갱신과 아크플롯 갱신은 이 경로에서 실행하지 않는다.
- [ ] 저장 직전에 같은 출처의 활성 사건 여부를 다시 확인하고, 기존 사건을 덮어쓰지 않는 원자적인 생성 검사를 추가한다. 소스 집합 순서 변경과 기존 리부트 묶음 사건도 중복 테스트에 포함한다.
- [ ] 각 턴이 성공한 뒤에만 해당 분석 영수증을 갱신한다. 과거 작중 시간을 현재 시각에서 추정하지 않는다.
- [ ] 생성한 사건은 공통 원문 순서 계산을 사용한다. 1, 4, 5턴 사건이 있는 상태에서 2, 3턴을 복구한 뒤 목록이 1~5 순서인지, 기존 아크 체크포인트보다 앞선 복구 사건을 새 진행분으로 잘못 세지 않는지 검증한다. 이미 작성된 아크 본문 보완은 별도 범위로 남긴다.
- [ ] 사건 내용이 없거나 모델 출력이 잘렸다면 임의로 1턴 1문서를 강제하지 않고 사유를 표시한다.
- [ ] 취소, 파일 저장 실패 시 다음 턴을 시작하지 않고 이미 완료한 턴과 미처리 턴을 구분한다. 같은 요청 재시도에서 성공한 사건을 중복 생성하지 않는다.

## Task 4: 관련 인물의 작중 행적만 보완

**Files:** `src/ts/risubard/bardChatTurnRepair.ts`; `server/node/risubard-memory-analysis.ts`; `server/node/risubard-markdown-section-patch.ts`; `src/ts/risubard/wikiWritingLanguage.ts`; 관련 테스트.

**Interfaces:** 행적 제안은 검증된 기존 인물 ID, 근거 사건 ID, 원문 근거와 삽입 위치를 가진 추가 항목이다. 전체 인물 문서 교체나 임의 절 삭제 요청을 받지 않는다.

- [ ] 사건이 이미 존재하지만 행적만 빠진 사례를 테스트한다. 사건 생성 여부와 독립적으로 인물 보완 필요성을 확인한다.
- [ ] 명확한 인물 링크와 검증된 원문을 사용한다. 단순 언급만으로 사건 참여나 비밀 습득을 단정하지 않는다.
- [ ] `작중 행적` 및 기존 언어별 동등한 절을 대상으로 기존 내용을 보존하는 삽입만 허용한다. 같은 사건의 같은 정보는 추가하지 않는다. 이름과 근거가 모호하면 미적용 처리한다.
- [ ] 선택한 위키 정책이 `주요 전환` 등 다른 구조를 사용하는 경우 임의로 절 이름을 바꾸거나 새 행적 절을 만들지 않는다. 지원되는 행적 절이 없다는 이유를 표시하고 그 인물은 건너뛴다.
- [ ] 현재 상태뿐 아니라 관계, 지식과 비밀, 인물 핵심 등 다른 절을 원문 그대로 유지하는 프로그램 검사를 둔다. 모델 지시문만으로 보호했다고 주장하지 않는다.
- [ ] 정렬에는 원문 순서를 사용한다. 알 수 없는 날짜를 지어내지 않고 기존 행적을 재정렬하거나 재요약하지 않는다.
- [ ] 내용 hash가 달라졌으면 해당 인물 저장을 거부한다. 재시도는 최신 문서에서 중복을 다시 확인한다.
- [ ] 긴 인물 문서 끝의 행적을 보완한 뒤 앞부분과 다른 절의 바이트 동일성을 검사한다. 행적 자체가 입력 예산을 넘으면 기존 구간 처리 기반을 사용하거나 저장 없이 실패를 알린다.

## Task 5: 바드챗 연결과 완료 판정

**Files:** `src/lib/Others/RisuBardWikiCommandTerminal.svelte`; `src/lib/Others/RisuBardMemoryWiki.svelte`; `src/ts/risubard/bardChatCommandTemplates.ts`; `src/ts/risubard/directWikiCommand.ts`; 각 테스트와 최신 패치노트.

- [ ] 예시 요청 `140~144턴의 누락된 사건을 복구하고 관련 캐릭터의 작중 행적도 보완해`를 대상 확인 화면에 연결한다.
- [ ] 사용자가 확정한 대상에서만 실행하며 진행 중 취소를 제공한다. 일반 위키 편집 요청은 기존 경로를 유지한다.
- [ ] 결과는 사건 생성 수, 기존 사건 유지 수, 인물 행적 보완 수, 제외/실패/미처리를 구분한다. 기존 `적용 0건 + 문서 ID 필요` 대신 실제 사유를 표시한다.
- [ ] `복구 전 세이브`를 표시하고 재시작 후에도 찾아 복원할 수 있는지 확인한다. 저장 성공만으로 복원 성공을 주장하지 않는다.
- [ ] 6~8개 AI 턴과 두 인물의 임시 데이터로 전체 흐름을 검증한다. 화면 전환, 재실행, 중간 실패와 복원까지 포함한다. 100턴 수동 테스트를 요구하지 않는다.

- [ ] 관련 프런트엔드, 서버, 저장 호환성 테스트 및 타입 검사를 통과시킨다. 일반 바드챗 문서 수정과 개별 재분석의 기존 테스트도 유지한다.
- [ ] 이 조건을 만족한 실제 구현만 패치노트에 반영한다. 합성 테스트 통과와 실제 장기챗의 회수율 보장은 구분한다.

## 이번 재확인의 결론

기존 기능을 연결하는 것만으로 완성할 수 있다는 앞선 설명은 불충분했다. 빠진 부분은 범위와 원문 확정, 누락 전용 사건 저장, 행적만 수정하는 제한, 중복 방지 및 재시작 후 복원이다. 그 경계를 먼저 검증한 뒤 구현 여부를 판단하며, 계획 작성 자체를 기능 완료로 보고하지 않는다.
